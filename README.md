# pvtshiiiiii

A private messenger for two iPhones, built on [Scriptable](https://scriptable.app). It sends end-to-end encrypted text, photos, videos and voice notes. Everything expires after 24 hours. Supabase stores ciphertext only.

## Files

| Path | What it is |
| --- | --- |
| `src/page.html` | The app UI and all the crypto. It runs inside Scriptable's WebView. **Edit this.** |
| `src/native.js` | The Scriptable side: Keychain bridge, share/export, and the home-screen widget. **Edit this.** |
| `pvtshiiiiii.js` | Generated by `tools/build.mjs`. This is what the phones run. Don't edit it by hand. |
| `pvtshiiiiii.js.sig` | ECDSA P-256 signature of `pvtshiiiiii.js`. Always push it together with that file. |
| `pvtshiiiiii-auto-updater.js` | Install it on each phone by hand. It verifies the signature, refuses downgrades, then runs the app. |
| `supabase/002_keys_and_media.sql` | v2 server setup: the handshake table, the `publish_key` RPC, and the private media bucket with its RLS. |
| `tools/` | Build, signing and tests. |

## Step-by-step: getting it running

### What goes into Scriptable

| File | Paste into Scriptable? |
| --- | --- |
| `pvtshiiiiii.js` | **Yes, for the first test (Part C).** It's the whole app in one file, about 100 KB. |
| `pvtshiiiiii-auto-updater.js` | **Yes, for everyday use (Part E).** It's a small script that downloads, verifies and runs `pvtshiiiiii.js`. |
| `pvtshiiiiii.js.sig` | No. It goes to GitHub only. |
| `src/page.html`, `src/native.js` | No. These are the source files; the build turns them into `pvtshiiiiii.js`. |
| `supabase/*.sql` | No. This goes into the Supabase SQL Editor. |
| `tools/`, `package.json`, `README.md` | No. These stay on your computer. |

Both phones share the same Keychain items. That means you can pair with the pasted app in Part C, switch to the updater in Part E, and stay paired.

### Part A: Computer (once)

1. Install [Node.js](https://nodejs.org) 18 or newer.
2. Open a terminal in this folder and run:
   ```
   npm install
   npm test
   ```
   Every suite should end with `0 failed`. The first run downloads test browsers, which takes a few minutes.
3. **Back up the signing key** at `C:\Users\Admin\.pvtshiiiiii\release-signing-key.pem` to somewhere offline, such as a USB stick or a password manager. Never commit it or share it. Whoever has it can ship code to both phones.

### Part B: Supabase (once)

1. Open your project in the [Supabase dashboard](https://supabase.com/dashboard).
2. Go to **Authentication → Sign In / Providers** and check that **Allow anonymous sign-ins** is on.
3. Go to **SQL Editor → New query**, paste the whole of `supabase/002_keys_and_media.sql`, and click **Run**. You should see "Success. No rows returned". Running it twice is safe.
4. Back on your computer, run:
   ```
   node tools/smoke-supabase.mjs
   ```
   It should end with `supabase smoke: 15 passed, 0 failed`. It adds a little harmless test data to your project.

### Part C: First test, pasting the app directly (both phones)

Do this before pushing anything, to confirm the app works on your iPhones.

1. Get `pvtshiiiiii.js` onto each iPhone. Pick whichever is easiest:
   - **iCloud Drive (easiest):** on the PC, copy `pvtshiiiiii.js` into `iCloud Drive\Scriptable\`. iCloud for Windows must be installed, and Scriptable's iCloud sync must be on. The script appears in Scriptable by itself.
   - **Copy and paste:** open `pvtshiiiiii.js` on the PC, select all, copy, and send it to yourself (for example in Notes). On the iPhone, open Scriptable, tap **+**, paste, and tap the title to rename it to `pvtshiiiiii`.
2. On iPhone 1, tap the script to run it.
   - If you used the old version, you'll see **Security upgrade**. Tap **Upgrade and pair again**.
   - Tap **Create a space**, then choose a 6-digit passcode. Tap **ABC** to use letters instead; 8+ letters is stronger.
   - The **Invite your partner** sheet appears. Tap **Share** and send the invite privately, or tap **Copy**.
3. On iPhone 2, within 10 minutes:
   - Run the script, then tap **Join with an invite**.
   - Tap **Paste from clipboard** (or paste the invite by hand), then **Continue**.
   - Choose this phone's own passcode.
4. Both phones now show the chat. Open **⋯ → Safety number** on both. Compare the 30 digits in person or on a call. If they match, tap **Mark as verified**.
5. Test everything on the device checklist at the bottom of this file. If the app can't save, for example it keeps returning to the start screen, open `src/native.js`, set `strictCsp: false`, rebuild with `node tools/build.mjs`, and paste the app again.

### Part D: Publish to your new GitHub account (once)

1. Create a **public** repo on the new account. Public is fine: the code holds no secrets, and the Supabase key in it is designed to be public.
2. In `pvtshiiiiii-auto-updater.js`, set:
   ```js
   baseUrl: "https://raw.githubusercontent.com/<your-user>/<your-repo>/main/",
   ```
3. Commit and push this folder:
   ```
   git remote add origin https://github.com/<your-user>/<your-repo>.git
   git add -A
   git commit -m "pvtshiiiiii v2"
   git push -u origin main
   ```
   `.gitignore` already keeps out `node_modules`, `test-output` and any `.pem` file.
4. Check that GitHub serves exactly what you signed:
   ```
   node tools/check-remote.mjs
   ```
   Both lines must print `true`.

### Part E: Switch the phones to the auto-updater (both phones)

1. On the PC, open `pvtshiiiiii-auto-updater.js` (the copy with your `baseUrl`), select all and copy it. It's small, so pasting it through Notes is fine.
2. In Scriptable, open your existing `pvtshiiiiii` script, delete everything in it, paste the updater, and tap **Done**. Also delete the old v1 updater script if you still have it.
3. Run it. It downloads the app, checks the signature and opens the chat. You're still paired.
4. Add the widget:
   - Long-press the Home Screen, tap **+**, choose **Scriptable** and add the small widget.
   - Long-press the widget, tap **Edit Widget**, set **Script** to `pvtshiiiiii`, and set **When Interacting** to **Run Script**.

The widget shows only an unread count, never message text.

### Releasing an update later

1. Edit `src/page.html` or `src/native.js`.
2. Increase the version in `// APP_VERSION:` (top of `src/native.js`) and in `version:` (in `CONFIG`).
3. Run `npm test`, then `node tools/build.mjs`. This rebuilds and re-signs.
4. Push `pvtshiiiiii.js` and `pvtshiiiiii.js.sig` in the same commit, then run `node tools/check-remote.mjs`.

The phones pick up the update the next time they open the app. They refuse anything unsigned, tampered with, or older than what they already have.

### Troubleshooting

| You see | Fix |
| --- | --- |
| "The server is missing the v2 setup" | Run Part B step 3. |
| "Enable anonymous sign-ins" | Turn on Part B step 2. |
| "That invite is invalid or expired" | Invites last 10 minutes and work once. On iPhone 1, open **⋯ → Invite partner** for a new one. |
| "Unverified device joined" or "Key mismatch" | Someone other than your partner may have used the invite. Go to **⋯ → Reset this phone** on both phones and pair again. |
| The updater says "No verified copy" | Check `baseUrl`, check that both files were pushed, then run `node tools/check-remote.mjs`. |
| You forgot your passcode | On the lock screen, tap **Forgot passcode?**. This resets the phone, and you'll need to pair again. |
| Voice notes say recording isn't available | Allow the microphone under iOS **Settings → Scriptable**. Or send a recording with **+ → Audio file**. |

## How the security works

- **Pairing.** Each phone generates an ECDH P-256 key pair.
  - The invite is `PVT2.<code>.<fingerprint of creator key>.<one-time secret>`. It contains **no encryption key**.
  - The joiner checks that the creator's key matches the fingerprint. The creator checks the joiner's HMAC with the one-time secret.
  - Both phones derive the message key with HKDF.
  - A 30-digit safety number lets you rule out an active man-in-the-middle by comparing it in person or on a call.
- **Messages.** Each message is AES-256-GCM encrypted.
  - The space id is bound in as additional authenticated data.
  - The sender id is sealed inside the ciphertext, so the server can't re-attribute or forge messages.
  - The server sees `message_type = 'text'` for every message, so it can't tell photos, videos and voice notes apart, except by their size.
- **Media.**
  - Every file gets its own random key. The key and the file's storage path travel inside the encrypted message.
  - Photos are re-encoded through a canvas, which strips EXIF data including GPS location. Videos are sent as recorded, so their metadata is not stripped.
- **On the phone.** Keys live in a vault sealed with your passcode (PBKDF2-SHA256 with 600k iterations, then AES-GCM).
  - Failed passcode attempts persist across launches and back off up to 1 hour.
  - The app is meant to auto-lock 60 s after you leave it. This relies on Scriptable firing `visibilitychange`; see the checklist.
  - The widget only reads an unread count. It never touches the vault.
- **Updates.** The updater verifies an ECDSA P-256 signature in pure JS (Scriptable has no WebCrypto) before running anything, including its cached copy.

**Limits, stated plainly**

- **The passcode vault slows an attacker down; it doesn't stop one.** All Scriptable scripts share one Keychain. A malicious script could copy the vault and brute-force a 6-digit code offline. A letters passcode of 8+ characters makes that much harder.
- **There's no forward secrecy.** One message key is used per pairing. Re-pair to rotate it.
- **The server still sees some metadata:** who talks to whom, when, and how big each message is.
- **Saving media shares a plaintext copy.** "Save or share" hands a decrypted copy to iOS (Photos, Files, AirDrop), and that copy doesn't expire.
- **Anyone can sign up and use storage.** The repo is public, so anyone holding the publishable key can sign up anonymously, create a space and upload 50 MB files to your Storage, at your cost. Turn on Supabase's anonymous sign-in rate limits and CAPTCHA. Watch Storage usage, and consider a per-space object cap in `is_member_path`.
- **Expired files are cleaned up only when a phone opens the app.** Each phone deletes expired files on launch. For guaranteed cleanup, add a scheduled Edge Function.

## Tests

`npm test` runs four suites:

| Suite | What it covers |
| --- | --- |
| `test-updater` | The updater's whole flow under a Scriptable shim. Covers a valid release, a tampered download, the wrong signing key, a downgrade, a 404, offline use, an upgrade, a tampered cache, recovery, and a missing key. |
| `test-verifier` | 188 cross-checks of the updater's SHA-256 and ECDSA verifier against Node `crypto` |
| `build --no-sign` | Compatibility, CSP and `RESET_ALL` guards |
| `e2e` | Two simulated phones in WebKit, plus Chromium with a fake mic for voice. Covers pairing, text, photo, video, voice, export, safety numbers, tamper and forgery rejection, a bad joiner, a server-swapped key, lock and lockout, token refresh, and media cleanup. The Supabase mock includes RLS-equivalent checks. |
| `e2e-native` | The **built** `pvtshiiiiii.js` running under a Scriptable API shim. Covers the real bridge, the Keychain whitelist, chunked export to QuickLook with temp cleanup, the legacy upgrade, reset, and the widget. |

Screenshots are written to `test-output/`. Two paths are implemented but not covered by any test: recovering from a dead refresh token during setup, and the full "Forgot passcode?" reset (the in-chat Reset is tested).

## On-device checklist

These can't be checked from a desktop, so test them on a phone:

- [ ] Auto-lock fires after 60 s in the background, and Lock now works.
- [ ] The bridge works under the CSP. If Keychain writes fail, set `CONFIG.strictCsp = false`.
- [ ] Polling keeps running while the app is open (the WebView reports itself as visible).
- [ ] The microphone works in Scriptable's WebView (`getUserMedia`). If it doesn't, the app falls back to choosing an audio file.
- [ ] The camera and library pickers open, and a recorded video sends.
- [ ] The keyboard doesn't cover the composer.
- [ ] QuickLook appears over the app when you tap Save or share.
- [ ] A video around 45 MB doesn't run out of memory.
- [ ] The updater verifies quickly enough on the phone (BigInt), including from the widget.
